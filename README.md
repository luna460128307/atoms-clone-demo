# Atoms Clone Demo —— Agent 驱动的应用生成器

一个参考 [atoms.dev](https://atoms.dev/) 交互体验实现的可运行 Demo：用户用一句自然语言描述想要的应用，"多智能体团队"（PM / 架构师 / 工程师 / QA）协作分析需求、设计数据模型、生成代码，最终产出一个真实可交互、数据可持久化的小应用，并可在页面右侧实时预览与操作。

## 访问方式

本 Demo 未部署到公网（已与需求方确认无需在线链接），以本地运行的方式交付。

```bash
cd atoms-clone-demo
npm install
npm start
# 访问 http://localhost:3000
```

Node.js 版本要求 >= 18。首次访问需要注册一个账号（用户名至少 3 位，密码至少 6 位），所有数据保存在 `data/store.json` 中，重启服务不会丢失。

代码仓库已在本地初始化 Git 并完成提交（`git log` 可查看），未推送到任何远程仓库。

## 核心交互流程

1. 注册 / 登录账号（服务端 session + bcrypt 密码哈希 + JSON 文件持久化）。
2. 在左侧对话框输入一句需求描述，例如"帮我做一个待办事项清单"。
3. 对话区实时展示 PM Agent → Architect Agent → Engineer Agent → QA Agent 四个角色依次产出的分析过程（需求解析、数据建模、接口与代码生成、自测校验）。
4. 智能体协作过程播放完毕后，先展示一张虚线边框的"生成计划"确认卡片（模板类型、字段设计摘要），用户点击「确认并生成」才会真正创建应用并落库；点击「重新描述」可以直接放弃本次计划、重新输入需求，不会产生垃圾数据。
5. 确认后自动在右侧面板中加载一个真实可交互的应用（真实的表单提交、勾选、点赞、投票、状态流转、库存加减、指标录入等操作，均落库持久化）。
6. 侧边栏保存历史生成记录，可随时切换回看、删除，或对已有应用重新生成（迭代需求）。
7. 支持将生成应用的完整源码打包为 zip 下载，解压后 `npm install && npm start` 即可独立运行，脱离本平台单独使用。

## 实现思路与关键取舍

**为什么不接入真实大模型 API：** 评审 / 演示环境通常无法保证外部 LLM API Key、网络出口和调用额度稳定可用，一旦生成失败会导致"Demo 在别人电脑上跑不起来"的尴尬局面。因此本 Demo 用"关键词匹配 + 模板渲染"的规则引擎（`server/agentEngine.js`）模拟多智能体的分工产出，重点保证生成出的应用是真实、可交互、可持久化的产品，而不是一段假动画。引擎与运行时之间做了解耦：如果未来要换成真实 LLM 驱动的代码生成，只需要替换 `agentEngine.js` 里的 `planWithAgents`（输入需求文本，输出模板配置 + 分析过程文案），不需要改动运行时、存储层、前端交互逻辑。

**为什么用 JSON 文件持久化而不是 SQLite/MySQL：** 最初尝试用 `better-sqlite3`，但它依赖原生编译（node-gyp），在当前沙箱环境的 Xcode Command Line Tools 版本探测上直接编译失败，且很多零成本部署平台对原生模块支持有限，容易出现"本地能跑、线上跑不起来"的问题。改用一个基于 JSON 文件、带写队列串行化和原子替换的极简数据库封装（`server/db.js`），零原生依赖，读写效率对 Demo 级别的数据量完全足够，且是真实落盘而非内存假数据，重启服务、关闭浏览器都不会丢失数据（已通过重启进程后数据仍在的测试验证）。

**为什么内置八套模板而不是"万能代码生成"：** 完全通用的代码生成（生成任意结构的数据库表 + 任意页面布局）在没有真实 LLM 的情况下很难做到稳定可靠，容易变成"看起来智能、实际上跑不起来"的效果。因此选择了八个在真实业务中最常见、覆盖面较广的 CRUD 场景（待办事项、留言板、投票、打卡、预约管理、CRM 客户管理、商品库存管理、业务数据看板），通过关键词打分匹配用户意图。八套模板共享同一套运行时 API 和前端渲染框架（按字段类型动态生成表单和列表），保证"一次投入，多场景复用"的架构可扩展性；字段类型系统也从最初的 text/textarea/number/boolean 扩展出了 `select`（枚举状态流转，用于预约状态、CRM 销售阶段）和 `formHidden`（标记该字段不出现在新建表单里，而是通过列表上的按钮交互维护，例如点赞数、票数、连续打卡天数、状态徽章），服务端对 select 的枚举值和 number 的 `min` 下限都做了防御性校验（POST 和 PATCH 两处都生效），不会因为绕过前端直接调用 API 而破坏数据完整性。

**兜底策略的取舍：** 当用户描述完全无法匹配任何预置模板的关键词时，早期版本的做法是静默降级成留言板模板，这样用户会困惑"我明明要的是别的东西，为什么给我一个留言板"。现在的兜底逻辑改为使用最通用的留言板结构承接需求的同时，在 PM Agent 的分析文案里如实说明"未能精确匹配到预置模板，已保留原始需求摘要"，让用户清楚知道发生了什么，而不是被一个看似正常、实则文不对题的结果误导。

**为什么要做两步式生成确认，而不是一步直接生成：** 一步直接生成的问题在于，如果 PM Agent 对需求的理解跑偏了（比如兜底走了不合适的模板），用户往往要等应用生成完、切到预览面板试了几下才发现不对，需要删除重来，体验上有一次浪费。改为先展示模板类型、字段设计摘要等"生成计划"，用户确认无误后再真正创建落库，能在信息更少的成本下让用户及时纠偏。实现上 `/api/projects/plan` 只做需求解析和模板选择、不做任何数据库写入，`/api/projects/confirm` 才真正创建项目，且服务端不信任前端在确认请求里回传的模板数据、而是重新计算一遍，避免被篡改。

**数据看板模板为什么要做成真实聚合而不是静态数字：** 业务数据看板这类模板很容易偷懒做成一堆写死的假数字卡片，看起来有模有样但完全不能反映真实数据、也经不起交互验证。这里刻意把看板做成基于用户实际提交的指标记录，按指标名称分组求和，动态计算统计卡片总数、累计值和柱状图各分组的占比，哪怕只是 Demo 级别的实现也要保证"看到的数字是真的"。

**关于"基本流程 + 延展能力"的覆盖：** 基本流程覆盖了注册、登录、核心的"描述需求 → 生成计划确认 → 生成 → 预览交互"主链路；延展能力覆盖了历史项目管理（列表、切换、删除）、二次生成（迭代需求）、源码导出下载三项，其中源码导出这一项呼应了 Atoms 强调的"代码所有权"这一差异化卖点——用户拿到的不是锁定在平台里的黑盒，而是一份可以直接 `npm start` 独立运行的真实项目代码。

## 目录结构

```
atoms-clone-demo/
├── server/
│   ├── index.js         # Express 服务入口、路由挂载、session 配置
│   ├── db.js             # JSON 文件持久化封装（用户/项目/生成应用的运行时数据）
│   ├── auth.js            # 注册/登录/登出/当前用户
│   ├── agentEngine.js     # 核心：多智能体协作模拟引擎（需求解析 -> 模板选择 -> 过程文案）
│   ├── projects.js        # 生成应用主流程 + 项目管理 + 源码导出
│   ├── runtimeApp.js       # 生成应用的真实运行时 CRUD API
│   └── codeExport.js       # 把生成应用渲染成一套独立可运行的 Node.js 源码
├── public/
│   ├── index.html / app.js / style.css   # 主平台前端：登录、对话式生成、项目侧栏
│   └── preview.html                       # 生成应用的真实交互预览页（iframe 内嵌）
├── data/                  # 运行时数据持久化目录（store.json，已加入 .gitignore）
└── package.json
```

## 当前完成度

已完成：账号注册登录与会话保持；自然语言需求解析与模板匹配（八种模板：待办/留言板/投票/打卡/预约/CRM/库存/数据看板，关键词打分 + 更诚实的兜底策略）；两步式生成交互（先出计划确认卡片，用户确认后才真正创建）；多智能体协作过程的可视化展示；生成应用的真实增删改查交互与数据持久化（重启不丢失，已实测验证），含状态流转（select 类型 + 枚举校验）、库存加减（number 类型 + min 下限防御性校验，防止越权 API 调用写入负库存）、数据看板的真实动态聚合统计；历史项目管理（列表、切换预览、删除）；二次生成/迭代需求；生成应用源码打包下载并验证可独立运行（新模板同样支持）；深色主题 UI，交互体验参考 Atoms 官网的三栏布局（侧边栏 + 对话流 + 实时预览）。

未完成 / 已知限制：未接入真实大模型，需求理解停留在关键词匹配层面，无法处理关键词库之外的复杂/组合型需求；未做多人协作、团队空间等企业级功能；数据库是单文件 JSON，未做索引和分页，数据量增长后需要迁移到真正的数据库；未接入用户头像上传、第三方登录（如飞书/企业微信 SSO）；未做移动端适配（当前布局面向桌面宽屏设计）；未部署到公网（已与需求方确认，本次以本地运行方式交付）；未加限流、验证码等防刷机制，仅适合 Demo 级别的可信环境使用；session 采用内存存储，服务进程重启会导致登录态失效（需要重新登录），但用户账号和项目数据本身持久化在 JSON 文件中不受影响。

## 未来延展方向

如果继续投入，优先级从高到低建议：其一，替换 `agentEngine.js` 为真实 LLM 驱动（可接入的模型不限），把"关键词匹配"升级为"自由文本理解 + 代码级生成"，同时保留现在的模板机制作为生成失败时的兜底与效果对照基线；其二，把 JSON 文件存储替换为真正的数据库（如 PostgreSQL/MySQL），支持多用户高并发写入与更复杂的数据查询；其三，支持模板可插拔机制，允许生成"字段级自定义"的应用而不局限于现有八套预置模板，比如让 Architect Agent 可以动态定义任意字段组合；其四，补充团队协作、应用发布分享（生成一个公开可访问的短链接给应用，类似 Atoms 的"一键发布"）、内置支付/登录等生产级组件模板；其五，补充自动化测试与 CI，以及一键部署脚本（Docker 化 + 常见 PaaS 平台的部署配置模板）。

## 关键验证记录

开发完成后进行了两轮端到端验证。第一轮（基础四模板）：接口层面测试了注册、登录、会话保持、四种模板的生成、CRUD 增删改查、数据持久化文件内容、重启进程后数据仍在、源码导出 zip 内容完整性、导出后的独立项目可以单独 `npm install && node server.js` 运行并响应接口请求；界面层面用浏览器自动化验证了登录/注册表单渲染与提交、生成流程的智能体协作过程动画、生成后自动加载到预览面板、在预览面板中真实提交数据并勾选完成状态、界面状态实时更新。

第二轮（模板库扩展到八种 + 两步式交互）：接口层面测试了 `/api/projects/plan` 不产生副作用、`/api/projects/confirm` 正确落库；预约/CRM 模板的状态流转（含枚举校验，非法状态返回 400）；库存模板的 min:0 下限修复验证（POST 和 PATCH 传入负数均被服务端纠正为 0）；数据看板模板基于真实提交记录的分组聚合计算结果正确；CRM 项目跨服务重启的数据完整性；导出的 CRM 独立项目单独运行后完整验证了增删改查全流程。界面层面用浏览器自动化完整走通了"输入需求 → 智能体协作过程展示 → 生成计划确认卡片 → 点击确认并生成 → 预览面板真实交互"的全流程，并对 CRM 状态流转按钮、库存加减按钮（含越界不跌破 0）、数据看板统计卡片与柱状图的真实渲染效果做了截图验证，均符合预期。
